## ADR-001 — Управление секретами: переменные окружения

**Дата:** 2026-04-17  
**Статус:** Принято  
**Задача:** Фаза 0, задача 0.1  

---

### Контекст

В исходном монолите три секрета хранились открытым текстом прямо в `application.properties`, который находится в git-репозитории:

```properties
spring.datasource.password=12345
jwt.secret=super-secret-key-change-me-please-32chars
openai.api.key=YOUR_OPENAI_API_KEY
```

Аналогично в `docker-compose.yml`:
```yaml
POSTGRES_PASSWORD: 12345
```

**Риски текущего состояния:**
- Любой человек с доступом к репозиторию (публичному или приватному с утечкой) получает полный доступ к БД и может подделывать JWT-токены
- OpenAI API key — платный ресурс, утечка приведёт к финансовым потерям
- Это уязвимость класса **A02:2021 – Cryptographic Failures** из OWASP Top 10

---

### Рассмотренные варианты

#### Вариант 1: Переменные окружения + `.env` файл ✅ ВЫБРАН

Секреты переносятся в файл `.env`, который добавляется в `.gitignore`. В `application.properties` остаются только ссылки:

```properties
spring.datasource.password=${DB_PASSWORD}
jwt.secret=${JWT_SECRET}
```

**Плюсы:**
- Стандарт индустрии (принцип №3 методологии 12-Factor App)
- Нулевая сложность реализации — Spring Boot поддерживает `${VAR}` из коробки
- Легко объяснить на защите диплома
- Docker Compose нативно читает `.env` файл из той же директории
- Разработчик видит `.env.example` и понимает какие переменные нужны

**Минусы:**
- `.env` файл на диске разработчика не зашифрован — если машина скомпрометирована, секреты утекут
- Нет аудит-лога: непонятно кто и когда менял значения
- Не подходит для команды из 5+ человек (нужно как-то синхронизировать `.env`)

---

#### Вариант 2: Spring Cloud Config Server с зашифрованными значениями

Spring Cloud Config поддерживает шифрование значений через `{cipher}` префикс:

```yaml
# в config-server репозитории
jwt:
  secret: '{cipher}AQBXz3k9P...'
```

Для расшифровки нужен symmetric key или keystore, передаваемый через переменную `ENCRYPT_KEY`.

**Плюсы:**
- Зашифрованные секреты можно хранить в git
- Централизованное управление конфигами (важно для микросервисов)
- Config Server запланирован в архитектуре (Фаза 1)

**Минусы:**
- Требует поднятого Config Server даже для локальной разработки
- Усложняет onboarding: новый разработчик должен знать `ENCRYPT_KEY`
- `ENCRYPT_KEY` сам является секретом — проблема не исчезает, только сдвигается
- Избыточно для Фазы 0 монолита

**Вывод:** Актуален в Фазе 1+ когда Config Server уже поднят. Для Фазы 0 — преждевременно.

---

#### Вариант 3: HashiCorp Vault

Выделенный сервер для хранения секретов. Spring Boot имеет интеграцию через `spring-cloud-vault`.

```yaml
spring:
  cloud:
    vault:
      uri: http://localhost:8200
      token: ${VAULT_TOKEN}
```

**Плюсы:**
- Промышленный стандарт для production-систем
- Динамические секреты (Vault может выдавать временные credentials к БД)
- Полный аудит-лог: кто, когда, какой секрет запросил
- Rotation секретов без перезапуска приложения

**Минусы:**
- Vault — ещё один сервис в инфраструктуре (нужно ставить, настраивать, бэкапить)
- Steep learning curve: unsealing, policies, auth methods
- Для дипломного проекта одного разработчика — значительный overhead
- `VAULT_TOKEN` сам является секретом (та же проблема сдвига)
- Избыточно до тех пор, пока нет команды и реального production

**Вывод:** Правильное решение для production с командой. Для учебного проекта — over-engineering.

---

#### Вариант 4: Зашифрованный `.env` через git-crypt или SOPS

`git-crypt` или Mozilla SOPS позволяют хранить зашифрованные файлы прямо в git. Ключ шифрования хранится отдельно (GPG ключ или AWS KMS).

**Плюсы:**
- Зашифрованные секреты в репозитории — удобно для команды
- SOPS поддерживает частичное шифрование (только значения, ключи видны)

**Минусы:**
- Требует настройки GPG или облачного KMS
- Дополнительный инструмент вне экосистемы Spring/Java
- Для одного разработчика избыточно

**Вывод:** Хорошее решение для команды без Vault. Для дипломного проекта — лишняя сложность.

---

### Принятое решение

**Переменные окружения + `.env` файл** — для Фазы 0 и всей локальной разработки.

Обоснование выбора:
1. **Соответствует задаче:** устраняет критическую уязвимость (секреты в git) с минимальной сложностью
2. **Стандарт:** 12-Factor App принят как best practice в индустрии, понятен любому проверяющему
3. **Путь к усложнению:** в Фазе 1 при создании Config Server можно перенести конфиги туда; в production — подключить Vault. Переменные окружения совместимы с обоими вариантами
4. **Дипломный контекст:** задача проекта — показать понимание принципов, а не развернуть enterprise-инфраструктуру

---

### Последствия и что делать дальше

| Среда | Рекомендуемое решение | Фаза |
|---|---|---|
| Локальная разработка | `.env` файл (текущее решение) | Фаза 0 ✅ |
| Dev/Staging окружение | Config Server + зашифрованные значения | Фаза 1 |
| Production | HashiCorp Vault или облачный secrets manager (AWS Secrets Manager, GCP Secret Manager) | За рамками диплома |

**Важно:** секрет `JWT_SECRET` используется и в монолите, и будет использоваться в `api-gateway` (для валидации токенов). При переходе к микросервисам оба сервиса должны получать **один и тот же** секрет из одного источника. Это ещё один аргумент в пользу Config Server в Фазе 1.

## ADR-002 — Настройка CORS: список конкретных origins вместо wildcard

**Дата:** 2026-04-17  
**Статус:** Принято  
**Задача:** Фаза 0, задача 0.2

---

### Контекст

В исходном коде CORS был настроен с `allowedOriginPatterns("*")` в сочетании с `allowCredentials(true)`:

```java
configuration.setAllowedOriginPatterns(List.of("*"));
configuration.setAllowCredentials(true);
```

Это комбинация опасна: браузер отправляет cookie и Authorization-заголовки (credentials) на **любой** origin, включая вредоносные сайты. Это открывает вектор для CSRF-атак через авторизованные cross-origin запросы.

Технически Spring выбрасывает исключение если задать `setAllowedOrigins("*")` + `setAllowCredentials(true)` — именно поэтому в коде использовался `setAllowedOriginPatterns("*")`, что обходит эту проверку, но проблему безопасности не устраняет.

---

### Рассмотренные варианты

#### Вариант 1: Оставить `"*"` без `allowCredentials` ❌

Убрать `setAllowCredentials(true)` и оставить wildcard. Браузер перестанет слать cookies и заголовки аутентификации на чужие origin'ы.

**Проблема:** приложение использует JWT в заголовке `Authorization` — это не cookie, но `allowCredentials(false)` также запрещает кастомные заголовки в некоторых браузерах. На практике это сломает авторизацию с фронтенда.

#### Вариант 2: Конкретный список origins из переменной окружения ✅ ВЫБРАН

```java
@Value("${app.allowed-origins}")
private String allowedOrigins;

configuration.setAllowedOriginPatterns(Arrays.asList(allowedOrigins.split(",")));
```

В `.env`:
```
ALLOWED_ORIGINS=http://localhost:3000
```

В production `.env`:
```
ALLOWED_ORIGINS=https://app.nutrifit.kz,https://admin.nutrifit.kz
```

**Плюсы:**
- Устраняет уязвимость: только перечисленные origins получают доступ
- Конфигурируется без изменения кода — достаточно поменять переменную окружения
- Поддержка нескольких origins через запятую (dev + prod одновременно при необходимости)
- Совместимо с `allowCredentials(true)` — Spring принимает конкретные паттерны

**Минусы:**
- Нужно явно добавлять каждый новый frontend-origin в переменную — нельзя забыть при деплое

#### Вариант 3: Конфигурация через Spring Security `httpSecurity.cors()` ❌

Альтернативный способ настройки CORS непосредственно в `SecurityConfig` вместо отдельного бина.

**Отклонён:** текущая архитектура уже использует отдельный `CorsConfigurationSource` бин, который явно передаётся в `SecurityConfig`. Менять структуру ради этого нет смысла.

---

### Принятое решение

Список origins читается из переменной окружения `ALLOWED_ORIGINS`. Значения разделяются запятой — это позволяет задавать несколько origins без изменения кода.

```java
// CorsConfig.java — итоговое решение
configuration.setAllowedOriginPatterns(Arrays.asList(allowedOrigins.split(",")));
```

---

### Почему CORS важен — для защиты диплома

CORS (Cross-Origin Resource Sharing) — механизм браузера, который ограничивает какие сайты могут делать запросы к API. Без правильной настройки:

1. Вредоносный сайт `evil.com` делает запрос к `api.nutrifit.kz` от имени залогиненного пользователя
2. Браузер добавляет credentials (заголовки аутентификации) автоматически
3. API отвечает с данными пользователя — это и есть CSRF

Конкретный список origins гарантирует, что только доверенные фронтенд-приложения могут делать авторизованные запросы.

---

### Последствия

При добавлении нового фронтенда (мобильное приложение, admin-панель) — добавить его origin в `ALLOWED_ORIGINS` в `.env` нужного окружения. Код менять не нужно.

## ADR-003 — Миграции схемы БД: Flyway вместо `ddl-auto=update`

**Дата:** 2026-04-17  
**Статус:** Принято  
**Задача:** Фаза 0, задача 0.3

---

### Контекст

Исходный проект использует `spring.jpa.hibernate.ddl-auto=update`. При каждом старте Hibernate сравнивает Java-сущности со схемой в БД и применяет изменения автоматически.

**Риски `ddl-auto=update`:**
- Hibernate **не удаляет** столбцы и таблицы — накапливается "мусор" в схеме
- Нет истории изменений: невозможно понять, когда и какое изменение было применено
- Поведение в production непредсказуемо: `update` может заблокировать таблицу при добавлении столбца с NOT NULL без DEFAULT
- Нет rollback: если деплой прошёл частично — откатить схему нельзя
- Это антипаттерн для любой серьёзной системы (проверяющий увидит и оценит)

---

### Рассмотренные варианты

#### Вариант 1: Flyway ✅ ВЫБРАН

Flyway — инструмент версионирования схемы БД. Миграции — это SQL-файлы с именем `V{версия}__{описание}.sql`. Flyway хранит историю применённых миграций в таблице `flyway_schema_history`.

```
src/main/resources/db/migration/
    V1__init_schema.sql    ← текущий, описывает начальную схему
    V2__add_column.sql     ← будущий, добавит новый столбец
```

**Плюсы:**
- Полная история всех изменений схемы в git
- Детерминированность: одинаковая схема на dev, staging, production
- Безопасный деплой: если миграция не прошла — приложение не стартует
- Нативная интеграция со Spring Boot: применяет миграции до старта приложения
- Стандарт индустрии, известен любому Java-разработчику

**Минусы:**
- SQL-файлы нельзя изменять после применения (Flyway проверяет checksum)
- Нужно писать SQL вручную, а не полагаться на автогенерацию Hibernate

**Особенность Flyway 10.x + Spring Boot 3.x:** поддержка PostgreSQL вынесена в отдельный артефакт `flyway-database-postgresql`. Без него Flyway стартует, но не видит PostgreSQL-диалект.

#### Вариант 2: Liquibase

Аналог Flyway, но миграции описываются в XML/YAML/JSON (`changeSet`), а не чистом SQL.

**Плюсы:**
- Поддерживает rollback (changeSet может иметь `<rollback>` секцию)
- Абстракция над диалектом: один changeSet работает на PostgreSQL, MySQL, Oracle

**Минусы:**
- XML/YAML синтаксис сложнее читать и отлаживать
- Избыточная абстракция для проекта с одной БД (PostgreSQL)
- Диплом: SQL понятнее проверяющему, чем Liquibase XML

**Вывод:** Liquibase оправдан при поддержке нескольких СУБД. Для этого проекта — лишняя сложность.

#### Вариант 3: Оставить `ddl-auto=update`

**Отклонён:** не решает проблему, создаёт риски в production, не подходит для дипломного проекта уровня "знаю как правильно".

---

### Принятое решение

**Flyway** с двумя зависимостями (`flyway-core` + `flyway-database-postgresql`) и конфигурацией:

```properties
spring.flyway.baseline-on-migrate=true
spring.flyway.baseline-version=0
```

**Почему `baseline-on-migrate=true`:**  
БД уже существует (создана `ddl-auto=update`). Без baseline Flyway откажется работать — он увидит таблицы, но не найдёт `flyway_schema_history` и решит, что это "грязная" БД. С `baseline-on-migrate=true` Flyway создаёт `flyway_schema_history` и помечает версию 0 как baseline (уже применена). Затем применяет V1 (1 > 0).

**Почему `CREATE TABLE IF NOT EXISTS` в V1:**  
На существующей БД таблицы уже есть — `IF NOT EXISTS` делает SQL idempotent (запрос проходит без ошибки). На чистой БД таблицы создаются нормально. Это позволяет V1 работать в обоих сценариях.

**Правило: NOT NULL колонки без явного SET в коде требуют DEFAULT в SQL:**  
Пример — `profiles.onboarding_completed`. В Java `boolean` инициализируется `false` автоматически, поэтому Hibernate всегда вставляет значение явно — на существующей БД проблемы нет. Но если запустить на чистой БД без `DEFAULT false` и по какой-то причине Hibernate пропустит поле (или кто-то вставит строку напрямую через SQL), PostgreSQL выдаст `NOT NULL violation`. Правило: если колонка имеет `NOT NULL` и представляет состояние со значимым начальным значением (флаг, статус, счётчик) — добавляй `DEFAULT` в SQL. Колонки-данные (`email`, `password`, `user_id`) DEFAULT не нужен — они всегда передаются явно из бизнес-логики.

---

### Последствия

- Все последующие изменения схемы (добавить столбец, создать таблицу) — только через новый файл `V{N}__описание.sql`
- Существующие файлы миграций **нельзя изменять** — Flyway проверяет checksum и откажется стартовать
- Задача 0.4 переключит `ddl-auto=update` → `ddl-auto=validate`: Hibernate будет только проверять соответствие сущностей и схемы, но не изменять схему
